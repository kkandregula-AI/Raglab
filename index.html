Step 2 · Embed & Index

The vector store, made visible

Each chunk is converted into a vector — a list of numbers describing its meaning — and placed in an embedding space. Similar meaning → nearby points. This map is a live 2-D projection of your chunks. Run a query in Step 3 and the query star ★ will appear here, connected to its nearest chunks.

What a chunk looks like inside the store

Real systems use dense embeddings (e.g. 1,024–3,072 dimensions from an embedding model) stored in a vector database — Pinecone, Weaviate, Qdrant, Milvus, pgvector, Chroma. Track B · Fine-Tuning

Fine-tuning: teaching the model itself

RAG gives a model an open book. Fine-tuning changes the model's handwriting — its weights — so behaviour, tone, and domain fluency are baked in. In classical terms: RAG is Smṛti (recalled from an external store), fine-tuning is Saṃskāra (impressions carved into the model itself).

The types of fine-tuning

Sample dataset — try the JSONL validator

Fine-tuning data is usually JSONL: one training example per line, in chat messages format. Edit below and validate — the checks mirror what real pipelines enforce.

Maintaining datasets so answers stay grounded

A fine-tuned model is only as honest as its data. The discipline:

  • Version everything. Treat datasets like code: dataset-v2026.07, changelogs, and a data card describing sources and licences.
  • Quality over quantity. 500–5,000 excellent, human-reviewed examples usually beat 100k noisy ones for behaviour tuning.
  • Deduplicate & decontaminate. Remove near-duplicates and make sure eval questions never leak into training data.
  • Teach refusal. Include “I don't know / not in our records” examples so the model learns to say so instead of hallucinating.
  • Hold out an eval set. Freeze 10–20% as test questions with gold answers; score every new model version against it before shipping.
  • Refresh on a cadence. Policies change — schedule quarterly re-reviews; retire stale examples the way you retire stale docs in RAG.
  • Log real failures back in. The best new training examples are yesterday's wrong answers, corrected by a human.

RAG vs Fine-tuning — when to use which

QuestionChoose RAGChoose Fine-tuning
Does the knowledge change often?Yes — update the index, not the modelRetraining for every policy edit is costly
Do you need citations / audit trail?Yes — chunks are traceable sourcesWeights can't cite themselves
Is it about tone, format, style, workflow?Prompting helps, but driftsYes — behaviour lives in weights
Domain jargon the base model garbles?PartiallyDomain-adaptive tuning shines
Latency / prompt-size budget tight?Context adds tokensKnowledge is “free” at inference
Small team, fast start?A RAG MVP is a weekend projectNeeds data pipeline + evals
Real answer for most companies: both. Fine-tune (or just prompt-tune) the behaviour; RAG the facts. Grounded tone + grounded truth.

Track D · Connect outward

Wiring RAG into MCP & tools

A vector store answers one question: “what do we know?” Real workflows need actions too. MCP (Model Context Protocol) is the open standard that lets any model talk to your company systems — including your RAG store — through one plug.

The agentic RAG loop

User ──▶ Model (Claude / any MCP client)
              │  decides which tool it needs
              ├──▶ search_knowledge_base(query)   ← your vector store as an MCP server
              ├──▶ crm.lookup_customer(id)        ← Salesforce / Zoho MCP
              ├──▶ drive.fetch_doc(path)           ← Google Drive MCP
              └──▶ tickets.create(payload)        ← Jira / Linear MCP
              ▼
        Grounded answer + completed action, with sources

The shift: RAG stops being a fixed pipeline and becomes one tool among many that the model calls when it decides retrieval is needed — often multiple times, refining its query each round (agentic / self-RAG).

Your vector store as an MCP server

Expose retrieval as a tool. Any MCP-capable client (Claude apps, Claude Code, IDEs, your own PWA) can then use it:

{ "name": "search_knowledge_base",
  "description": "Search Aarambh Motors' curated company docs. Returns top-k chunks with sources.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "top_k": { "type": "integer", "default": 3 } },
    "required": ["query"] } }

Same schema works as a plain tool in the Anthropic Messages API (tools:[…]) or as an MCP server tool — MCP simply standardises discovery, auth, and transport.

Build order for a company

  • 1 · Pipeline RAG — what SMṚTI demos: ingest → chunk → embed → retrieve → answer. Ship this first.
  • 2 · Tool-calling RAG — give the model a search_knowledge_base tool; it retrieves only when needed, and can re-query.
  • 3 · MCP server — wrap the same retrieval in an MCP server so every AI surface in the company (chat, IDE, agents) shares one governed memory.
  • 4 · Actions — add write-tools (create ticket, draft email, update CRM) behind human approval. Retrieval + action = a real digital colleague.
  • 5 · Governance — per-tool permissions, audit logs of every retrieval and action, and role-based filtering of which chunks each employee's assistant may see.
