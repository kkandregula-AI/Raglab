Chunking best practices

Chunking quality decides retrieval quality — most "RAG doesn't work" complaints are chunking problems. The discipline:

  • Split on semantic units, not raw characters. Sentences, paragraphs, and headings are natural boundaries; never cut mid-sentence. (SMṚTI splits on sentences, then packs to size.)
  • Typical size: 200–500 tokens (~300–800 chars). Too small → answers lose context; too big → similarity scores blur and irrelevant text rides along into the prompt. Drag the slider above and watch retrieval quality change.
  • Overlap 10–15%. A little repetition at boundaries means a fact straddling two chunks is never lost. (See the trailing words repeated at each chunk start above.)
  • Prepend context to every chunk. Adding the document title and section to the chunk text ("HR Leave Policy › Carry-forward: …") dramatically improves matching — called contextual chunking.
  • Respect structure. Never split a table row, code block, or numbered list mid-structure; chunk them whole with their heading.
  • Store rich metadata. Doc name, version, date, access level per chunk — needed for citations, freshness filtering, and permissions later.
  • Measure, don't guess. Keep 20 test questions with known source chunks; tune chunk size/overlap until top-3 retrieval hits ≥90% of them.

Track B · Fine-Tuning

Fine-tuning: teaching the model itself

RAG gives a model an open book. Fine-tuning changes the model's handwriting — its weights — so behaviour, tone, and domain fluency are baked in. In classical terms: RAG is Smṛti (recalled from an external store), fine-tuning is Saṃskāra (impressions carved into the model itself).

Maintaining datasets so answers stay grounded

A fine-tuned model is only as honest as its data. The discipline:

  • Version everything. Treat datasets like code: dataset-v2026.07, changelogs, and a data card describing sources and licences.
  • Quality over quantity. 500–5,000 excellent, human-reviewed examples usually beat 100k noisy ones for behaviour tuning.
  • Deduplicate & decontaminate. Remove near-duplicates and make sure eval questions never leak into training data.
  • Teach refusal. Include “I don't know / not in our records” examples so the model learns to say so instead of hallucinating.
  • Hold out an eval set. Freeze 10–20% as test questions with gold answers; score every new model version against it before shipping.
  • Refresh on a cadence. Policies change — schedule quarterly re-reviews; retire stale examples the way you retire stale docs in RAG.
  • Log real failures back in. The best new training examples are yesterday's wrong answers, corrected by a human.

How fine-tuning actually changes weights — live LoRA demo

A model is billions of numbers (weights). Fine-tuning nudges them. LoRA doesn't touch the base weights at all — it trains two tiny matrices A and B whose product ΔW = A·B is added on top. Below is real LoRA arithmetic on a toy 32×32 layer (illustrative numbers, genuine math):

W (base) — frozen
1,024 params

ΔW = A·B — trained
only 128 params (12.5%)

W + ΔW — the tuned model
behaviour changed, base intact

Notice ΔW's stripey pattern — that's the fingerprint of a low-rank update (rank 2 here). This is why LoRA is cheap: on a real 7B-parameter model, the same trick trains ~0.1–1% of the weights, and you can keep one small adapter file per department while sharing one base model.

Rule of thumb: if the answer should change when a document changes → RAG. If the answer should stay the same across all documents → fine-tuning. If unsure, start with RAG — it's cheaper, auditable, and reversible.

Do you need to "rent" a model? Subscriptions vs API vs your own weights

Three access models, and students mix them up constantly:

  • Consumer chat subscription (Claude, ChatGPT, Gemini apps — monthly plan). You're renting a finished assistant for yourself. Great for learning and personal work; many now support projects/file-upload, which is managed RAG on your documents. But it's not programmable — you can't build an app on it, and it does not include fine-tuning.
  • API (pay-per-token). You're renting raw model calls to build your own product — what SMṚTI would use with a key, and what any company assistant runs on. Costs scale with usage; RAG works by stuffing retrieved chunks into your prompts. Hosted fine-tuning, where offered, lives at this tier and varies by provider and model.
  • Open-weights models (Llama, Mistral, Qwen, Gemma families). You download the weights — nothing rented. Full fine-tuning freedom (LoRA on a single GPU or even a good laptop for small models), total data privacy, and this is where the sample JSONL datasets above would actually be used with tools like Hugging Face + PEFT or Unsloth. Cost shifts from per-token fees to hardware.

For learning RAG: this free app + a consumer subscription is genuinely enough. For learning fine-tuning: you don't need to rent anything — a small open-weights model (1–8B) plus a free Colab/Kaggle GPU and the datasets from this page is the standard student path. For a company product: API for the model, your own vector store for the memory, and fine-tune only when behaviour demands it — exactly the decision table above.

Track D · Connect outward

Wiring RAG into MCP & tools

A vector store answers one question: “what do we know?” Real workflows need actions too. MCP (Model Context Protocol) is the open standard that lets any model talk to your company systems — including your RAG store — through one plug.

The agentic RAG loop

User ──▶ Model (Claude / any MCP client)
              │  decides which tool it needs
              ├──▶ search_knowledge_base(query)   ← your vector store as an MCP server
              ├──▶ crm.lookup_customer(id)        ← Salesforce / Zoho MCP
              ├──▶ drive.fetch_doc(path)           ← Google Drive MCP
              └──▶ tickets.create(payload)        ← Jira / Linear MCP
              ▼
        Grounded answer + completed action, with sources

The shift: RAG stops being a fixed pipeline and becomes one tool among many that the model calls when it decides retrieval is needed — often multiple times, refining its query each round (agentic / self-RAG).

Your vector store as an MCP server

Expose retrieval as a tool. Any MCP-capable client (Claude apps, Claude Code, IDEs, your own PWA) can then use it:

{ "name": "search_knowledge_base",
  "description": "Search Aarambh Motors' curated company docs. Returns top-k chunks with sources.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "top_k": { "type": "integer", "default": 3 } },
    "required": ["query"] } }

Same schema works as a plain tool in the Anthropic Messages API (tools:[…]) or as an MCP server tool — MCP simply standardises discovery, auth, and transport.

Build order for a company

  • 1 · Pipeline RAG — what SMṚTI demos: ingest → chunk → embed → retrieve → answer. Ship this first.
  • 2 · Tool-calling RAG — give the model a search_knowledge_base tool; it retrieves only when needed, and can re-query.
  • 3 · MCP server — wrap the same retrieval in an MCP server so every AI surface in the company (chat, IDE, agents) shares one governed memory.
  • 4 · Actions — add write-tools (create ticket, draft email, update CRM) behind human approval. Retrieval + action = a real digital colleague.
  • 5 · Governance — per-tool permissions, audit logs of every retrieval and action, and role-based filtering of which chunks each employee's assistant may see.
